# 采用 React + TypeScript + Canvas/WebCodecs/WebAudio + Capacitor 构建 Android 优先原生应用

> 在 Windows 11 + WSL 开发环境下，面对双路视频 0.1x 超慢放同步、音频波形与 BPM 自动测算、三线/矩形框几何变换及所见即所得视频导出的综合需求，我决定采用 React + TypeScript + HTML5 Canvas/WebAudio/WebCodecs 配合 Capacitor 封装 Android 原生壳，以达成预览与导出 100% 像素级一致及快速跨端验证，并接受移动端 WebView/WebCodecs 编码器适配的代价。

## 考虑过的方案

| 方案 | 好处 | 代价 |
| --- | --- | --- |
| React + TS + Canvas/WebCodecs/WebAudio + Capacitor 原生壳 | Android Chromium 原生支持 0.0625x~16x 变速不变调；WebAudio 直接解码 PCM 测算 BPM、画波形与合成节拍器；预览与导出共用同一个 Canvas 渲染函数，无需手写复杂 FFmpeg 滤镜链 | 导出依赖 WebCodecs / MediaRecorder 或浏览器编码管线，大视频离线合成需控制帧步进与内存缓冲 |
| Flutter (Dart) + video_player + ffmpeg_kit | Flutter UI 渲染性能好，原生纹理直接显示 | ExoPlayer 在部分设备上低于 0.1x 变速受限；提取 PCM 测算 BPM 和导出复杂三线/并集画幅必须重写一套等价的 FFmpeg filter_complex，且上游 ffmpeg-kit 已归档停更 |
| React Native (Expo) + 原生音视频模块 | 生态成熟，JavaScript 开发 | 同样存在原生视频组件超慢放同步精度差、预览布局与 FFmpeg 导出滤镜需要双端重复实现的问题 |

## 决定

选 **React + TS + Canvas/WebCodecs/WebAudio + Capacitor 原生壳**，因为：
1. Chromium 内核的 `HTMLVideoElement.playbackRate` 官方支持 `0.0625 ~ 16.0` 且内置 `preservesPitch = true`，天然覆盖 `0.1x` 乘以 BPM 变速比后的超慢放区间且保持变速不变调。
2. `WebAudio API` 可以直接将视频音轨解码为 Float32 PCM 数组，在纯前端内完成音频波形绘制、自动 BPM 测算和毫秒级精度的合成节拍器。
3. 预览画面与视频导出完全共用同一个 `renderComparisonFrame(ctx, state)` 画布渲染函数，从根本上杜绝“预览是一套坐标计算、导出拼 FFmpeg 又是另一套坐标计算”导致的对齐偏差。

## 代价

- 我们接受：需要配置 Capacitor Android 工程以支持强制横屏锁定与系统相册文件保存。
- 我们放弃：不引入复杂的原生 C++ 音视频编解码桥接层。
- 后面要还的债：在导出长时长 0.1x 慢放视频时，需要提供清晰的导出进度反馈与取消机制。

## 什么情况下需要重新讨论

- 如果目标 Android 设备的系统 WebView 版本过旧且不支持 WebCodecs / Canvas 视频录制，需要回退到原生插件合成时，重开这条记录。
