# 导出区间调整停止与单帧预览渲染机制

> 在导出工作台拖动起止点 A 和 B 易与播放状态冲突且导致预览黑屏的处境下，面对高频寻道导致的解码器雪崩、状态错位与黑屏假死的顾虑，我决定在触发调整起止点时强制停止播放并重置控制按钮为「预览」，同时建立 RAF 驱动的实时渲染循环与上一帧画面防黑屏保持策略，以达成起止点拖拽画面精准实时跟随且交互状态严谨一致的目标，并接受导出页前台常驻轻量 RAF 循环的极微性能开销。

## 考虑过的方案

| 方案 | 好处 | 代价 |
| --- | --- | --- |
| 方案 A：允许播放中拖拽 A/B 并持续边播边调（维持原状修补） | 用户无需手动再按播放 | 移动端解码器高频 `playFrom` 与 `seek` 极度不稳定，容易疯狂掉帧、音画撕裂或卡死，且起止点定义本身代表选定静态画面边界，边播边调不符合剪辑操作直觉 |
| 方案 B：纯事件监听驱动（在 `seeked` 事件中调用单次 `drawPreviewFrame`） | 无需维护持续渲染动画循环 | 移动端双视频事件触发时机不一，高频拖动下事件容易乱序或被中间 epoch 取消，导致最终帧重绘遗漏，极难彻底根除黑屏 |
| 方案 C（本方案）：**调整前置强制停止 + RAF 循环驱动 + 旧帧防黑屏保持** | 状态机绝对清晰，左下角按钮与播放状态 100% 同步；无论高频拖拽或低频点击，只要解码器吐出新帧，下一帧 RAF 立即上屏，彻底消除黑屏与假死 | 导出页在挂载期间需运行轻量 RAF 渲染循环，离开时需正确销毁 |

## 决定

选 **方案 C**，因为：
1. **交互逻辑符合直觉与第一性原理**：剪辑动作起止点（A/B 点）的本质是“寻找并确认特定瞬间的帧动作”。用户拖动手柄时，核心诉求是看清当前手柄对准的那一帧。强制暂停播放能够立即释放硬件解码资源，完全避免寻道雪崩，同时将左下角按钮归位至「预览」，消除了“视频已停但按钮是暂停”的逻辑错乱；
2. **彻底解决黑屏根因**：原先黑屏主因是 `renderComparisonFrame` 在寻道中间态执行了 `fillRect('#000000')` 纯黑清屏，且高频拖拽丢弃了 `onComplete` 回调导致画面停留在纯黑。方案 C 通过 RAF 持续捕获视频就绪帧，并在中间态保持已有画面，从机制上根除了黑屏死锁。

## 代价

- 我们接受：在导出页激活时由 `requestAnimationFrame` 驱动渲染循环，退出导出页时清理该循环；
- 我们放弃：在拖拽 A/B 过程中维持视频自动前向播放的非标准体验；
- 后面要还的债：未来若扩展多端点标定，需统一复用该前置停止与单帧对齐状态机。

## 什么情况下需要重新讨论

- 如果移动设备在超低功耗模式下对后台 RAF 循环有严苛限制且出现显著卡顿，需重新评估基于事件驱动加锁的高可靠单次渲染方案。
