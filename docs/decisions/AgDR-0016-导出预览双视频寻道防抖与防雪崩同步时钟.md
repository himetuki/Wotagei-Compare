# 双视频寻道防抖与防雪崩同步时钟

> 在导出工作台（ExportPage）与对比工作台（Workbench）由用户拖动进度条后再点击播放的场景下，面对底层 HTMLVideoElement 异步寻道未完成与 RAF 高频循环重复赋 currentTime 导致的单侧死锁卡顿（Seek Thrashing）问题，我决定引入「起播就绪栅栏 + 寻道互斥节流 + 锁相环防雪崩追赶（冷却隔离与 seeking 互斥）+ 自适应音轨主时钟」，以达成双视频拖拽后立即播放丝滑流畅、声画严格对齐的目标，并接受增加微量就绪等待时间（通常 < 50ms）的代价。

## 考虑过的方案

| 方案 | 好处 | 代价 |
| --- | --- | --- |
| 方案 A：仅修复导出界面，对比台保持现状 | 改动集中在单个组件 | 对比台在大跨度拖拽与高码率视频下依然会偶发单侧卡顿，问题未能彻底解决 |
| 方案 B：粗暴调大 diff 容差阈值（例如从 0.25s 调大到 0.8s） | 改动极小，仅改一个数值参数 | 治标不治本；在用户远距离拖拽跳转时，初始 diff 必然远超 0.8s，依然会在 RAF 中触发连续打断寻道死循环；且大容差会导致两视频出现长达近一秒的肉眼可见音画动作错位 |
| 方案 C（本方案）：全工作台统一起播就绪栅栏 + 寻道互斥节流 + 锁相环防雪崩追赶（seeking 互斥与冷却隔离）+ 自适应主时钟 | 从第一性原理切断死循环链条；严禁在 seeking 时重复赋 currentTime；优先柔性变速追赶；结合起播就绪检查，彻底根除卡死，音画毫秒级平滑对齐，同时覆盖对比台与导出台 | 需在两个组件中维护轻量级的就绪与冷却时间戳状态标记 |

## 决定

选 **方案 C**，因为：
1. **统一根治病灶**：单侧卡顿的根本原因不是性能不够，而是 RAF 循环在 16ms 极短间隔内对正在执行寻道（`seeking === true`）的视频不断重新设置 `currentTime`，使浏览器底层解码器陷入无限重置的寻道雪崩（Seek Thrashing）。通过在硬跳转前严格检查 `!video.seeking` 并设置最小冷却间隔（600ms），从物理机制上彻底终结了雪崩循环。
2. **起播相位对齐**：当用户刚拖拽完进度条立刻点击播放时，通过起播就绪栅栏确认双视频均退出 seeking 且达到可播放就绪状态后再联合起播，避免了一端已跑、另一端仍在寻道的巨大初相位差。
3. **音轨源与主时钟一致**：根据所选声音源（视频 1、视频 2 或节拍器）动态选定主时钟驱动者，避免对发声视频进行强硬时间撕扯，杜绝爆音与音调抖动。

## 代价

- 我们接受：用户快速连击拖拽并点播放时，存在极短暂（几十毫秒）的就绪对齐微延迟，换取起播后的绝对平滑不卡顿。
- 我们放弃：单向硬绑死视频 1 为主时钟的粗暴简单做法。
- 后面要还的债：无。该同步状态机与锁相环机制在各组件内自洽实现，接口干净。

## 什么情况下需要重新讨论

- 如果未来移动端浏览器出现完全不支持 `seeking` 属性反映底层解码状态的异常 WebView 内核（目前主流 Chromium / Safari 均严格遵守 HTML5 媒体规范），重开这条记录。
