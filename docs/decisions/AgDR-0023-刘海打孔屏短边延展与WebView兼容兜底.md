# 刘海打孔屏短边延展与 WebView 兼容兜底

> 在真实 Android 打孔屏手机运行出现左侧 90px 避让白边且启动黑屏假死的处境下，面对不同厂商定制系统 WebView 内核老旧（如坚果 R2 出厂内核低于 Chrome 80，不支持 `??` 与 `?.`）与打孔屏避让策略差异的顾虑，我决定在 Android 原生层配置纯黑底色与 `shortEdges` 打孔延展模式，并将前端 Vite 构建目标从激进的前沿目标降级至 `es2018`（Chrome 70+），同时在 HTML 入口注入首屏全局错误可视化挂载面板，以达成横屏全屏无缝沉浸与启动异常完全自见的目标，并接受编译产物尺寸略有增加（将 `??` 与 `?.` 降级为临时变量三元判断）的代价。

## 考虑过的方案

| 方案 | 好处 | 代价 |
| --- | --- | --- |
| 方案 A：仅修改 CSS 边距与背景色，不改动 Android 原生层与构建 target | 不触碰原生 Android 文件与打包配置 | 无法解决 Android 系统窗口级强制 letterbox 产生的 90px 白条；更无法解决低版本 WebView 解析 ES2022 语法错误直接卡死的问题 |
| 方案 B：原生层配置 `shortEdges` + 纯黑窗口背景，Vite target 降级至 `es2018`，并在 HTML 注入全局未捕获异常监控面板（本方案） | 从原生窗口、编译语法到前端入口全链路根治打孔屏白条与老旧内核黑屏，万一有偶发异常能一秒看清报错堆栈 | 针对老旧语法的微量 helper 函数会轻微增加几个 KB 的 bundle 体积 |
| 方案 C：引入第三方 Sentry/Bugly 等重量级移动端 APM SDK | 拥有远程上报与云端监控功能 | 引入巨大 native/web 依赖，违反最简工程原则，增加配置复杂度 |

## 决定

选 **方案 B**。
1. 第一性原理明确证明：左侧 90px `#FAFAFA` 是系统在横屏检测到打孔且应用未声明 `shortEdges` 时触发的 Window 级避让白条。必须通过原生 `android:windowLayoutInDisplayCutoutMode="shortEdges"` 配合 `android:windowBackground="@android:color/black"` 才能彻底消除。
2. 真机实测坚果 R2 等 Android 10 机型的 System WebView 低于 Chrome 80，无法解析 ES2020 的空值合并 `??` 与可选链 `?.`。降级至 `es2018` 能完全将这些操作符转译为老旧内核支持的三元判断，覆盖绝大部分 Chrome 70+ 内核。
3. 注入纯原生的 10 行错误捕获脚本能够将黑屏致命错误以红色文字面板打印在屏幕上，让用户或测试人员随时截屏提供线索，成本极低但收益极高。

## 代价

- 我们接受：产物可能多出少量语法降级 helper 函数。
- 我们放弃：依赖极端前沿的 ES2022/ES2023 专有语法糖。
- 后面要还的债：无。

## 什么情况下需要重新讨论

- 如果未来项目全面切换为纯 WebAssembly/原生渲染管线或最低支持系统提升至 Android 15 且 WebView 保证全量自动更新。
