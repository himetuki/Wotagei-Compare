# 双视频代数守卫与严格会合起播状态机

> 在用户点击时间轴拖动滑块或「锚点前 1s」起播时，面对底层 HTMLVideoElement 异步寻道回调滞后触发导致的“点击暂停却单侧脱缰播放、跳转起播单侧卡顿”的严重状态竞争问题，我决定在 `DualVideoSyncEngine` 中引入「全局操作代数守卫（Epoch Guard）+ 寻道/时钟原子互斥 + 双端严格会合屏障（Deterministic Rendezvous Barrier）」，以达成双端起播严格同频、暂停绝对静止、绝无单侧脱缰与卡顿的目标，并接受增加微量就绪会合等待（约 10~50ms）的代价。

## 考虑过的方案

| 方案 | 好处 | 代价 |
| --- | --- | --- |
| 方案 A：在 React 组件层防抖（如对暂停按钮加锁、对滑块加 debounce） | 仅在 UI 层加几行 setTimeout | 治标不治本；根本病灶在底层异步事件与时钟循环的并发冲突，UI 节流无法阻断已经挂在底层 seeked 上的脏回调 |
| 方案 B：在 RAF 循环中直接调用 `play()` 唤醒落后视频 | 代码看似最简 | 致命缺陷：`video.play()` 为异步 Promise，在过渡期会被高频反复调用，产生滞后幽灵回调，导致暂停后单侧继续播放 |
| 方案 C（本方案）：全局代数守卫（Epoch Guard）+ 寻道原子挂起 + 双端会合屏障（Rendezvous Barrier） | 从第一性原理切断并发竞争；代数递增彻底作废所有滞后回调；拖拽时强制静默时钟；起播前等待双端完全就绪在同一时钟拍点联合起跑 | 需重构引擎内部的状态迁移管道 |

## 决定

选 **方案 C**，因为：
1. **彻底根除幽灵播放**：每次用户调用 `pause()`、`seekToTau()` 或改变意图时，递增 `epoch`。所有正在执行的底层 seek 任务捕获当时的 epoch；当触发 `seeked` 事件时，若当前 `epoch !== taskEpoch` 或意图不是播放，直接丢弃回调，绝不下发 `play()`。
2. **切断外部寻道与内部锁相环的竞态冲击**：在用户连续拖动时间轴或点击跳转时，强制将引擎置为 `SEEKING` 态并停用 RAF 锁相环，防止调速逻辑与目标寻道相互撕扯。
3. **消除初始相位差**：双端必须在同一时间点完成对齐与就绪确认，再共同发令 `play()` 并激活主时钟。

## 代价

- 我们接受：在点击跳转或起播时，等待双端共同完成就绪的极短耗时（通常 <50ms），换取起跑后的绝对同步与平滑。
- 我们放弃：在播放循环中盲目尝试重启未就绪视频的危险做法。
- 后面要还的债：无。该机制纯粹作用于引擎内部控制流。

## 什么情况下需要重新讨论

- 如果未来主流浏览器提供原生原子的联合播放 API（如重新规范化的 MediaController），可重开此记录。
